On October 6, the Microsoft for Developers blog published [What is Agent Experience (AX)?](https://developer.microsoft.com/blog/what-is-agent-experience-ax/), by Waldek Mastykarz. According to the post, AX is the experience an AI agent has when it discovers, chooses and uses a technology. One idea from the post guides this text: "a change that sounds agent-friendly can still make agents worse with your technology, or more expensive." Until you measure, it's a hypothesis.

Here I only look at usage: how an agent calls an API and checks the result.

Day to day, I build .NET APIs with contracts, authentication and permissions for different roles and applications, plus event-driven integrations. The examples below don't come from that work.

The material is a demo: a fictional customer-onboarding API in .NET 10, with synthetic data and two contracts, v1 and v2. In an experiment, an agent got the same task 12 times, 6 per contract; I cite the experiment's numbers along the way. Code, tests and data are [in the repository](https://github.com/brskt-dev/brskt-space/tree/main/demos/agent-ready-api). The demo and the experiment were built and run with Claude Code, from Anthropic, and the agent under test is also a Claude model, a limitation I come back to.

## Looks done. But did it work?

The v1 API grew around a web form that knows the plan ids, masks the CNPJ (the Brazilian company tax id) and has no plan field on its edit screen. For that form, it works.

Now swap the form for a client that only has the contract. Padaria Exemplo Ltda, a fictional bakery, is on Pro (id 2) and asked for Enterprise (id 3). The agents in the experiment tried a PUT like this (captured from the demo, not from a run):

```http
PUT /v1/requests/1
X-Api-Key: demo-key-acme-0001
Content-Type: application/json

{"email":"ana@exemplo.test","plan":3}

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"id":1,"name":"Padaria Exemplo Ltda","doc":"11222333000181","plan":2,"start":"2026-10-20","email":"ana@exemplo.test","st":0}
```

`200 OK`, and the body still says `"plan":2`. A code comment explains: plan changes are done by account managers in the back office, "so anything else in the body is ignored." One agent summed it up (agents reported in Portuguese; my translations): "The API accepts the request and ignores the plan without returning an error."

A 200 says the server answered, not that the goal was reached. Here the agent noticed, but nothing told it why.

In v1, if a create's response gets lost and the client resends, you get two onboarding requests. A demo test shows this; in the experiment, no agent resent.

Hence the question: can an API serve a frontend well and still trip up an agent?

## What changes when the caller is an agent

The frontend carries what the contract doesn't write down: plan ids, CNPJ format, which field is editable. The agent, a model calling the API on its own, has the OpenAPI document and the responses. With those, it chooses the operation and arguments, whether to retry, and what to report. What's valid, what the credential may do and what actually changed are up to the server.

<AgentApiFlow lang="en" />

Almost none of this is new. [OpenAPI](https://spec.openapis.org/oas/v3.2.1.html#introduction) presents itself as a way for humans and computers to understand a service without reading its code. A partner's script that only reads the docs hits the same walls. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) already says a client shouldn't automatically retry a non-idempotent request (where repeating repeats the effect) unless it can know the request is idempotent in practice, or that the original was never applied. The difference is a consumer that reads everything literally and then acts. "You can't change the model," the post says, but "everything the agent reads and calls is yours."

## The v1 contract and where it gets in the way

The v1 OpenAPI is generated from the C# records, with no descriptions (excerpt):

```json
"CreateBody": {
  "required": ["name", "doc", "plan", "start", "email"],
  "properties": {
    "doc": { "type": ["null", "string"] },
    "plan": {
      "pattern": "^-?(?:0|[1-9]\\d*)$",
      "type": ["integer", "string"],
      "format": "int32"
    },
    "start": { "type": ["null", "string"] }
  }
},
"UpdateBody": {
  "required": ["email", "plan"]
}
```

`plan` takes a number or a string and lists no values (you have to find `GET /v1/plans`). `UpdateBody` requires `email` and `plan` because it describes the record, not the behavior: all 6 v1 runs resent the email on every PUT, and three said it was because the field is required. A formatted CNPJ gets `400 {"error":"Invalid data"}`: one rejected create in every v1 run.

The PUT documents only the 200; the [spec](https://spec.openapis.org/oas/v3.2.1.html#responses-object) expects success and known errors.

| Problem | In v1 | Where v2 handles it |
|---|---|---|
| Ambiguous parameter | `doc` and `start` with no format; `plan` with no valid values | Contract |
| Incomplete docs | `plan` required, then ignored | Contract |
| Hard-to-read response | `st` is 0 or 1 | Verification |
| Error with no possible action | `Invalid data` | Errors |
| Result you can't check | 200 with the plan ignored | Errors |
| Retry that duplicates | resending creates another | Retries |
| Misread permission | back office only, with no warning | Permissions |

About `st`, one agent wrote: "I can't tell what stage the request is at." Nothing in this table is AI-specific.

## What changes in v2, and why

Same domain, contract rewritten for someone who only has the document and the responses. Each change answers one table row and has its limits.

### A contract you can follow

On create, the fields got clear names and descriptions:

```csharp
public sealed record CreateOnboardingRequest(
    // ...
    [property: Description("Customer's CNPJ: exactly 14 digits, no dots, slash or dash. Example: 45723174000110.")]
    [property: Required, RegularExpression(@"^\d{14}$", ErrorMessage = "Use exactly 14 digits, without dots, slash or dash. Example: 45723174000110.")]
    string CustomerTaxId,

    [property: Description("Plan the customer starts on.")]
    [property: Required(ErrorMessage = "Required. Use one of: basic, pro, enterprise.")]
    Plan? Plan,

    [property: Description("First day of service, as an ISO 8601 date (YYYY-MM-DD). Today or later, in UTC.")]
    [property: Required(ErrorMessage = "Required. Use an ISO 8601 date: YYYY-MM-DD.")]
    DateOnly? StartDate,
    // ...
    string ContactEmail);
```

These attributes become [schema metadata](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/include-metadata?view=aspnetcore-10.0) and, with `AddValidation()` in .NET 10, are [checked before the handler](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis?view=aspnetcore-10.0); without that line, [nothing is validated](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/validation?view=aspnetcore-10.0).

The v2 API separates looking up (`GET /v2/onboarding-requests?customerTaxId=`), validating (`POST /v2/onboarding-requests/validate`, no side effects) and executing (the `POST`). All 6 v2 runs validated before creating, and no create was rejected.

What this doesn't guarantee:

- `format: date` is only an [annotation](https://spec.openapis.org/oas/v3.2.1.html#data-type-format), and `pattern` is [not implicitly anchored](https://json-schema.org/draft/2020-12/json-schema-validation#section-6.3.3): without `^` and `$`, a JSON Schema validator would accept 14 digits inside a longer string (the demo's `pattern` has both).
- The ASP.NET Core 10 template [only serves the document in Development](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/openapi/overview?view=aspnetcore-10.0). The demo serves it on purpose: it's part of the contract.
- The document the agents tested didn't mark `Idempotency-Key` as required (headers [are optional by default](https://spec.openapis.org/oas/v3.2.1.html#common-fixed-fields)). An independent review caught this after the experiment; the fix was a transformer and a test that checks that field in the document. The [OpenAPI guide](https://learn.openapis.org/best-practices.html#use-a-design-first-approach) goes further: CI tools that check whether the code follows the description.

### Errors that tell you the next step

The v2 `PATCH` only changes `contactEmail`. If the body has `plan`:

```http
PATCH /v2/onboarding-requests/onb_560d8c1919
Content-Type: application/json

{"plan":"enterprise"}

HTTP/1.1 403 Forbidden
Content-Type: application/problem+json
X-Correlation-Id: c17d2db36ae44d41ea4899b814384b5f

{
  "type": "https://example.com/problems/plan-change-requires-approval",
  "title": "Changing the plan needs approval by an account manager.",
  "status": 403,
  "detail": "No changes were applied. Your credentials can request a plan change, not apply it.",
  "requiredScope": "plan-change:apply",
  "allowedAction": {
    "method": "POST",
    "href": "/v2/onboarding-requests/onb_560d8c1919/plan-change-requests"
  },
  "traceId": "00-c17d2db36ae44d41ea4899b814384b5f-492e51db2f1cff4f-00",
  "correlationId": "c17d2db36ae44d41ea4899b814384b5f"
}
```

Nothing was changed. The body is Problem Details, from [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html), which obsoletes 7807. `type` [identifies the problem](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1.1); `detail` is meant for people, and machines [shouldn't parse it](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.1.4). Machine-readable data go in [extension members](https://www.rfc-editor.org/rfc/rfc9457.html#section-3.2), like `requiredScope` and `allowedAction`. Internal details [stay out](https://www.rfc-editor.org/rfc/rfc9457.html#section-5).

| Status | In this demo | Retry? |
|---|---|---|
| 400 | invalid request | No, fix it |
| 403 | missing scope, or there's another way | No |
| 404 | wrong id, or an id from another tenant (the company that owns the credential) | No |
| 409 | same key still being processed | Yes, after `Retry-After` |
| 422 | same key, different body | No, use a new key |
| 5xx | server error | Yes, same key |

The same rule is in the v2 OpenAPI. RFC 9110 already asks clients [not to automatically repeat a 403](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4) with the same credentials.

v2 itself had two bugs, found while testing the demo: validation errors were keyed by the C# name (`CustomerTaxId`, not `customerTaxId`), and an invalid plan or date got a bare 400 "Bad Request" with no field. The fix goes through [CustomizeProblemDetails](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling?view=aspnetcore-10.0) and, for the second one, letting the JSON read error reach exception handling; now `"plan":"premium"` comes back with `"field":"plan"`.

The limit: no v2 agent sent `plan` through `PATCH`, and the operation's description already warned about the 403.

### Retrying without duplicating

`POST` [isn't idempotent](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2). The fix: the client sends one key per operation and repeats it on retries; the server returns the first attempt's result. That's one of the "means to know" RFC 9110 allows, though it doesn't mention this header. The v2 API follows the [Idempotency-Key header draft](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/), IETF work in progress, not a standard: revision 07 expired on April 18, 2026. No key: 400. Same key, different body: 422. Still in progress: 409 with `Retry-After: 1`. Already done: [the stored result](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html#section-2.6), with `Idempotent-Replayed: true`, as [Stripe](https://docs.stripe.com/error-low-level) does.

```csharp
var tenant = user.TenantId();
switch (idempotency.Begin(tenant, CreateOperation, idempotencyKey, IdempotencyStore.Fingerprint(body)))
{
    case IdempotencyStore.Outcome.Mismatch:
        return Problems.IdempotencyKeyReused();
    case IdempotencyStore.Outcome.InProgress:
        return Problems.RequestInProgress(http);
    case IdempotencyStore.Outcome.Replay(var done):
        http.Response.Headers["Idempotent-Replayed"] = "true";
        // ...
        return TypedResults.Created(done.Location, (OnboardingRequestResource)done.Body!);
    case IdempotencyStore.Outcome.Started(var entry):
        OnboardingRequest created;
        try
        {
            created = store.Create(tenant, /* ... */);
        }
        catch
        {
            // Nothing was created: free the key so a retry with it can go through
            idempotency.Forget(tenant, CreateOperation, idempotencyKey);
            throw;
        }
        var resource = created.ToResource(clock.GetUtcNow());
        entry.Complete(StatusCodes.Status201Created, resource.Links.Self, resource);
        // ...
        return TypedResults.Created(resource.Links.Self, resource);
    // ...
}
```

Entries are keyed by tenant, operation and key, with a SHA-256 fingerprint of the body. In the tests, ten parallel requests with the same key create one onboarding request, and a retry after a lost response gets the stored one. In the demo, a retry (the 201 body, omitted, is the original) and a different body with the same key:

```http
POST /v2/onboarding-requests
Idempotency-Key: 4b1f0c6e-demo-0003

HTTP/1.1 201 Created
Location: /v2/onboarding-requests/onb_560d8c1919
X-Correlation-Id: d97aeded577e11d400f606285e8a203f
Idempotent-Replayed: true

# same key, different body
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://example.com/problems/idempotency-key-reused",
  "title": "This Idempotency-Key was used with a different request.",
  "status": 422,
  "detail": "Nothing was created. Use a new key for a new request, or send exactly the same body to retry the original one.",
  "traceId": "00-66e903d306cf839611612d182c0fae43-82eca95e4fa5fbef-00",
  "correlationId": "66e903d306cf839611612d182c0fae43"
}
```

What this doesn't guarantee:

- **It isn't "exactly once."** The key only covers retries that reuse it, for 24 hours (`IdempotencyStore.Retention`). A new key is a new operation, and a 500 stays [indeterminate](https://docs.stripe.com/error-low-level#server-errors). And the draft asks you to publish the [expiration policy](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html#section-2.5.2) when there is one; the demo's contract doesn't say keys last 24 hours.
- **A failure midway.** If the create fails before the effect, the demo frees the key and the retry goes through; a test forces that failure. If it failed after the effect, the retry would duplicate. The demo's first version trapped the key in that case: retries got 409 until it expired.
- **Entries live in memory.** In production they must be durable and written in the same transaction as the effect. Something like this, illustrative and not part of the demo:

```sql
CREATE UNIQUE INDEX UX_IdempotencyKeys
    ON IdempotencyKeys (TenantId, Operation, IdempotencyKey);
-- written in the same transaction as the onboarding request's INSERT
```

- **No response? Look it up before resending.** The agent did that in all 12 runs.
- **The agents built readable keys**, like `onb-padaria-11222333000181-pro-20261020`: stable across attempts, but predictable and carrying the CNPJ. The draft warns that with low-entropy keys, attackers [may work out other keys and fetch other clients' stored responses](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html#section-5). Tenant scoping held: in round 2, two tenants sent the same key and each got its own onboarding request.

### Permissions decided on the server

Each credential (an `X-Api-Key`, demo-grade; a real system would use short-lived tokens) belongs to a tenant and has scopes. Scopes become [policies](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/security?view=aspnetcore-10.0) via `RequireAuthorization`, checked on the server on every call. `plan-change:apply` is never granted to integrations, and the document says so. The integration only requests the change:

```http
POST /v2/onboarding-requests/onb_560d8c1919/plan-change-requests
Idempotency-Key: 9d2e7a51-demo-0001
Content-Type: application/json

{"plan":"enterprise","reason":"Pedido do cliente."}

HTTP/1.1 202 Accepted
Location: /v2/plan-change-requests/pcr_45b0453bee
X-Correlation-Id: 9bca068808bec485068b2b16dfa902f2

{
  "id": "pcr_45b0453bee",
  "onboardingRequestId": "onb_560d8c1919",
  "requestedPlan": "enterprise",
  "status": "pending_approval",
  "statusDescription": "Waiting for an account manager. The onboarding request keeps its current plan until this is approved.",
  "createdAt": "2026-10-13T12:35:53.1168294+00:00",
  "self": "/v2/plan-change-requests/pcr_45b0453bee"
}
```

The model can be sure the customer wants Enterprise. The credential still lacks the scope, and that's what counts.

When a scope is missing, v2 says which one (`"requiredScope":["onboarding:write"]`) and that retrying won't help. That's guidance, not a grant.

Every read filters by the credential's tenant, so another tenant's id gets 404, not 403, which [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4) allows so as not to reveal that the resource exists.

The [Principles of AX](https://agentexperience.ax/concepts/principles-of-ax/) call it an anti-pattern to require a human when not strictly necessary, but accept it depending on the action's sensitivity, and ask that the agent be able to continue afterwards. Here, it resumes through the change request's id.

### How to know it worked

The create returns a stable id (`onb_…`), `Location` and `links.self`; the change request, its own id (`pcr_…`) and a URL. States have names and a `statusDescription` instead of `st: 0`. `pending_approval` says the current plan stays until approval: the feedback the Principles of AX ask for on actions that happen later.

Confirming means reading the state after the last change; the v2 runs did two or three such reads.

`X-Correlation-Id` is the request's W3C trace id and reappears in the error body and the audit log. The log keeps the credential's id, never the `X-Api-Key`, and no bodies or emails. But it keeps path, query and `Idempotency-Key` as they arrived, and the CNPJ ended up there: `"query":"?customerTaxId=11222333000181"` and the keys the agents built. The experiment protocol said otherwise; the correction is in an amendment. In production, hash or redact: personal data [shouldn't be written to logs as plain text](https://learn.microsoft.com/en-us/dotnet/core/extensions/data-redaction).

In the v2 reports, all six gave both ids and at least one `X-Correlation-Id`.

## Where MCP fits (and where you don't need it)

MCP (Model Context Protocol) is a protocol for offering tools to a model. It isn't required: the agents in the experiment used `curl`. The demo's adapter separates four layers:

1. **HTTP contract**: the OpenAPI document.
2. **Tool shown to the model**: name, description, `inputSchema` and [annotations](https://modelcontextprotocol.io/specification/2026-07-28/server/tools). The adapter exposes three tools; none applies a plan change.
3. **Client that makes the call**: holds the `X-Api-Key` (over stdio, credentials [come from the environment](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)), derives a stable `Idempotency-Key` from the arguments, and returns errors with `isError` and the Problem Details, so the model [can correct itself](https://modelcontextprotocol.io/specification/2026-07-28/schema).
4. **Server**: the same authorization and rules as any HTTP call. The adapter adds no rules.

```csharp
[McpServerTool(Name = "create_onboarding_request", Title = "Create onboarding request", Destructive = false, Idempotent = true, OpenWorld = false)]
[Description("Creates one onboarding request. Calling it again with the same arguments returns the same request, so it is safe to retry after a timeout. Returns the request with its id and status.")]
public Task<string> CreateOnboardingRequest(
    // ...
    [Description("CNPJ with exactly 14 digits, no punctuation. Example: 45723174000110.")] string customerTaxId,
    // ...
    CancellationToken ct)
{
    var body = new { customerLegalName, customerTaxId, plan, startDate, contactEmail };
    return api.SendAsync(HttpMethod.Post, "/v2/onboarding-requests", body, OnboardingApiClient.IdempotencyKey("create", body), ct);
}

// Program.cs
// The key comes from this server's configuration. The model never sees it and cannot pick another one.
http.DefaultRequestHeaders.Add("X-Api-Key",
    builder.Configuration["OnboardingApi:ApiKey"] ?? throw new InvalidOperationException("Set OnboardingApi:ApiKey."));
```

`Idempotent = true` is a hint: clients MUST treat annotations as [untrusted](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) unless the server is trusted. What protects the retry is the argument-derived key and the API, and only within 24 hours. The cost: two legitimate, identical requests within 24 hours become one.

The adapter uses the ModelContextProtocol 2.2.0 package, from the [official C# SDK](https://csharp.sdk.modelcontextprotocol.io/v2/concepts/getting-started.html), and passed a stdio test script on the current MCP revision, [2026-07-28](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning), and the previous one, 2025-11-25: `create twice, same id: True`, `invalid tax id -> isError: True`, `plan now: pro`. I haven't tested it with a model calling those tools.

## The experiment: what changed and what didn't

The protocol and 8 criteria were written before any run. Two amendments record later changes: round 2's setup, and the counting of two criteria, redone for round 1 too. The question: with the same task, agent and failure, does v2 lead to fewer wrong effects and a more faithful report? The task: open the onboarding request on Pro, switch it to Enterprise, and report what was done and what's pending.

There were 2 rounds × 2 contracts × 3 runs, each with its own credential and tenant. All 12 had an injected failure: the server saved the first accepted create and dropped the connection before answering (`curl: (56) Connection reset`). The agent, a Claude Code subagent on the same model as the session, was told to use only `curl`, and it read no files (the transcripts confirm this). Round 2 fixed two setup problems (the session's task list showed up in the agent's context, and v2's CNPJ example was the task's CNPJ) and gave the same result on every criterion.

| Criterion | v1 | v2 |
|---|---|---|
| Creates rejected before the accepted one | 1 in each run | 0 |
| Requests per run (including reading the OpenAPI) | 11 to 21 | 8 to 9 |
| Duplicates, or plan changed without approval | 0 | 0 |
| Report matches the server | 6 of 6 | 6 of 6 |
| Understood the plan-change rule | 0 of 6 | 6 of 6 |

From a v2 report: "I opened a plan change request, which is waiting for approval from an account manager."

No difference in duplicates, because the agent was careful: after the drop, it looked the request up and never resent. An unapproved plan change couldn't happen: neither server allows it.

Limits: 3 runs per contract per round; one model and one task; an API written for the article, with v1's problems known in advance; an assistant with a shell instead of typed tools; this site's CLAUDE.md in the agent's context (it doesn't mention the experiment); the failure always on the first create; cost not measured; the tested OpenAPI without `Idempotency-Key` marked as required. And the agent is a Claude model, the same kind that helped build the demo. As the post puts it, each result "holds for the scenarios and agent profile we measured"; this one doesn't show that v2 is better in general.

## Questions for people who build APIs and agents

- Do any of your operations return 200 and ignore part of the body?
- If the response gets lost, can the client find out from the API alone whether the effect happened?
- Which operations should wait for a person? Does the contract say so before the error does?
- What customer data ends up in your logs when a model builds the query and the key?
- For people building agents: does your client retry on its own? With which key?

If you've run into any of these, on either side, leave a comment below.

## Back to the plan change

In v1, the API answered 200, the plan stayed on Pro, and the agent asked for someone with system access to check, because the API never said who could make the change. In v2, it finished with the change request's id, knowing an account manager has to approve it and that the plan stays on Pro until then.

In these 12 runs, what separated v1 and v2 was cheap and old: names, a `pattern`, a description, a separate operation, a named status. The costlier protections were only exercised outside the experiment: the `Idempotency-Key`, in the tests and the MCP script; the structured 403, only in the tests.

Next tests, as hypotheses: a client that retries on its own, where the key should matter; other models; the MCP adapter driven by a model. Code, data and protocol are [in the repository](https://github.com/brskt-dev/brskt-space/tree/main/demos/agent-ready-api).
